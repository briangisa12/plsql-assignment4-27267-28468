# Implementation Notes

These notes explain how each program works, why it was designed that way, how errors are handled, and what we measured about performance.

---

## 1. Schema design

- **Identity columns** (`GENERATED BY DEFAULT AS IDENTITY`) generate the primary keys, so no sequences or triggers are needed.
- **Every constraint is named** (`pk_`, `fk_`, `uq_`, `ck_`). When a constraint is violated, the error message names the rule that was broken. For example, ORA-02290 on `CK_PRICE_POSITIVE` tells us immediately that a price became negative.
- **Business rules are also enforced by the database**, through `CHECK (qty_in_stock >= 0)`, `CHECK (unit_price > 0)` and the foreign keys. The PL/SQL validates first and gives friendly messages, but even code that bypasses our procedures cannot store invalid data.
- `UNIQUE (product_name, supplier_id)` allows the same product name for different suppliers ("USB Cable"). This is what makes the `TOO_MANY_ROWS` case realistic.
- `01_create_tables.sql` first drops the four tables with a loop over `USER_TABLES` and `EXECUTE IMMEDIATE`, so the script can be re-run without errors.
- Sample data uses `INSERT … SELECT` with name lookups instead of hard-coded IDs, so it still works if identity values differ.

## 2. Procedures

### 2.1 `p_record_stock_movement` (implicit cursors)
`(p_product_id IN, p_movement_type IN, p_quantity IN, p_note IN, p_new_qty OUT)`

1. Validates the quantity (> 0) and the movement type (`IN` / `OUT`), raising user-defined exceptions.
2. `SELECT qty_in_stock INTO … FOR UPDATE` reads the current stock and **locks the row**, so two sessions cannot sell the same stock at the same time. If the product doesn't exist, Oracle raises `NO_DATA_FOUND`.
3. For `OUT`, checks that there is enough stock.
4. `UPDATE … RETURNING qty_in_stock INTO p_new_qty` changes the stock and returns the new value in one statement. `SQL%ROWCOUNT` is printed.
5. `INSERT` into `stock_movements`, then `SQL%FOUND` confirms the row was written.
6. `COMMIT`. Every handler does `ROLLBACK` first, so the update and the insert are saved together or not at all.

### 2.2 `p_delete_supplier` (SQL%NOTFOUND, PRAGMA EXCEPTION_INIT)
`(p_supplier_id IN, p_rows_deleted OUT)`

- After the `DELETE`, `SQL%NOTFOUND` is TRUE when no row matched, which raises `e_supplier_not_found` (−20005). A DELETE that matches nothing **does not** raise `NO_DATA_FOUND`, which is why the implicit cursor attribute is needed.
- ORA-02292 (child record found) is given a name with `PRAGMA EXCEPTION_INIT(e_child_records_exist, -2292)`. The handler counts the supplier's products and raises a clear message (−20006). We deliberately let the foreign key detect the problem instead of checking first, because the constraint is always correct, even under concurrency.

### 2.3 `p_get_product_details` (%ROWTYPE records)
`(p_product_id IN, p_product_name OUT, p_supplier_name OUT, p_stock_value OUT, p_stock_status OUT)`

- `v_product products%ROWTYPE` and `v_supplier suppliers%ROWTYPE` are filled with `SELECT * INTO`. If a column is added to the table later, the record follows automatically.
- Status logic: qty = 0 gives `OUT OF STOCK`, qty < reorder level gives `REORDER NEEDED`, otherwise `OK`.
- Invalid IDs (NULL or ≤ 0) raise −20007; a missing product (`NO_DATA_FOUND`) raises −20008.

### 2.4 `p_supplier_stock_report` (explicit cursors, user-defined record, VARRAY)
`(p_supplier_id IN, p_total_value OUT, p_low_stock_count OUT)`

- **User-defined record** `t_report_line` holds one formatted report line: name, quantity, price, value and status.
- **VARRAY** `t_category_list` (max 10) collects the distinct categories. A VARRAY suits this because the list is small, ordered, and has a natural upper bound.
- **Explicit cursor with a parameter** `c_products(cp_supplier_id)`, processed with `OPEN / FETCH / EXIT WHEN %NOTFOUND / CLOSE`. `c_products%ROWCOUNT` gives the number of products, and a count of 0 raises `e_no_products` (−20010).
- **Cursor FOR loop** over `c_movements` prints the movement history. Oracle opens, fetches and closes it automatically.
- The `WHEN OTHERS` handler closes `c_products` if `%ISOPEN`, so an error never leaves a cursor open, then re-raises.

### 2.5 `p_bulk_price_adjust` (BULK COLLECT, FORALL, SAVE EXCEPTIONS)
`(p_category IN, p_amount IN, p_updated_count OUT, p_failed_count OUT)`

1. `FETCH c_products BULK COLLECT INTO v_ids, v_old_prices LIMIT 100` loads the products in batches of 100 into two **nested tables**.
2. `FORALL i IN 1 .. v_ids.COUNT SAVE EXCEPTIONS UPDATE …` sends the whole batch to the SQL engine in one call.
3. If any row fails (for example, a price that would become ≤ 0 and violate `CK_PRICE_POSITIVE`), the other rows are still updated and Oracle raises ORA-24381 at the end. We catch it as `e_bulk_errors` and loop over `SQL%BULK_EXCEPTIONS`:
   - `ERROR_INDEX` is the position in the collection, which leads to the product ID
   - `SQLERRM(-ERROR_CODE)` is the message
   - each failed index is stored in the **associative array** `t_failed_map` (`INDEX BY PLS_INTEGER`), so finding a failed row is a direct lookup
4. Successful rows are copied to new collections, and a second `FORALL INSERT` writes them to `price_change_log`.
5. `COMMIT`, then a summary line ("N processed, X updated, Y failed").

Each failed row is **reported, not hidden**: the caller gets `p_failed_count` and a line per failure.

## 3. Functions

| Function | Returns | Notes |
|---|---|---|
| `f_stock_value(product_id)` | NUMBER | qty × price. `NO_DATA_FOUND` becomes −20013. |
| `f_find_product_id(name, supplier_id DEFAULT NULL)` | product ID | `NO_DATA_FOUND` becomes −20014, `TOO_MANY_ROWS` becomes −20015. |
| `f_low_stock_products(category DEFAULT NULL)` | `t_name_list` | `BULK COLLECT` into a SQL-level nested table. An unknown category becomes −20016. |

- **Why the functions catch `NO_DATA_FOUND`:** when a function called from a SQL statement raises an unhandled `NO_DATA_FOUND`, Oracle treats it as "no value" and returns **NULL with no error**. A report would show an empty value instead of failing, which is a misleading result. Test E18 proves our version raises ORA-20013 in SQL.
- **`TOO_MANY_ROWS`:** `SELECT … INTO` must return exactly one row. Searching for "USB Cable" finds two. The optional `p_supplier_id` parameter is the fix: `f_find_product_id('USB Cable', 3)` returns 2.
- **Why `t_name_list` is created with `CREATE TYPE`:** a type declared inside PL/SQL is unknown to SQL. To query the result with `SELECT column_value FROM TABLE(f_low_stock_products)`, the type must exist at schema level.
- `BULK COLLECT` never raises `NO_DATA_FOUND`; it returns an empty collection. That's why the unknown-category check is a separate `COUNT(*)`.
- The functions have no `WHEN OTHERS`: unexpected errors propagate to the caller, which is exactly what `WHEN OTHERS THEN RAISE` would do. A handler like `WHEN OTHERS THEN RETURN NULL` would hide errors, so we don't use one.

## 4. Error handling strategy

1. **Validate early** and raise **named user-defined exceptions**, so the code reads like the business rules.
2. **Translate** every expected error into `RAISE_APPLICATION_ERROR` with a unique code and a message that includes the offending value.
3. **Name Oracle errors** we expect, with `PRAGMA EXCEPTION_INIT` (−2292, −24381).
4. **Undo partial work**: `ROLLBACK` in every handler of a procedure that changes data.
5. **Never swallow errors**: every `WHEN OTHERS` ends with `RAISE`.
6. The test scripts catch the errors with `WHEN OTHERS THEN DBMS_OUTPUT.PUT_LINE('Caught: ' || SQLERRM)`, only so that all tests can run in one script and each message stays visible.

## 5. Performance notes

### Why bulk processing is faster
PL/SQL code runs in the **PL/SQL engine**, and SQL statements run in the **SQL engine**. Every time a PL/SQL loop runs a SQL statement, control switches between the two engines (a **context switch**). A loop that updates 50,000 rows one by one makes 50,000 switches. `FORALL` sends all the rows in **one** switch, and `BULK COLLECT` brings many rows back in one switch.

### Measurement (`03_tests/performance_demo.sql`)
Run on our laptop (Oracle 26ai Free), 50,000 rows into a scratch table, timed with `DBMS_UTILITY.GET_TIME`. Two runs:

| Operation | Row by row | Bulk | Speed-up |
|---|---|---|---|
| INSERT 50,000 rows | 0.81 – 0.85 s (FOR loop + INSERT) | 0.04 – 0.05 s (FORALL) | about 17× |
| FETCH 50,000 rows | 0.14 s (explicit cursor, one FETCH per row) | ≤ 0.02 s (BULK COLLECT) | about 7× or more |

Exact times depend on the machine, but the ratio is consistent.

### Design decisions based on this
- **`LIMIT 100` in `p_bulk_price_adjust`:** `BULK COLLECT` without a limit loads *all* rows into memory (PGA). With a limit, memory stays small and constant however large the category grows, while still keeping almost all of the speed benefit.
- **`SAVE EXCEPTIONS`:** without it, one bad row stops the whole `FORALL` and the other rows are lost. With it, good rows are processed and bad rows are reported, so one bad value doesn't block a whole batch.
- **Cursor FOR loops:** since Oracle 10g, the compiler (at `PLSQL_OPTIMIZE_LEVEL` 2, the default) automatically fetches 100 rows at a time in a cursor FOR loop. A simple cursor FOR loop is therefore already efficient for reading, which is why `c_movements` uses one. Explicit `FETCH … INTO` one row at a time, and DML inside a loop, are **not** optimized. That's why bulk processing matters most for DML.
- **Single-row operations** (`p_record_stock_movement`, `p_get_product_details`) don't need bulk processing: they touch one row, so there is nothing to batch.
- **`SELECT … FOR UPDATE`** locks only the one product row being changed, which keeps concurrent sales correct without locking the whole table.
- **Functions in SQL** (`SELECT f_stock_value(product_id) FROM products`) run once per row and add a context switch for each row. They're fine for small tables. For large reports, the plain SQL expression `qty_in_stock * unit_price` would be faster; we use the function to demonstrate calling PL/SQL from SQL.

## 6. Testing approach
- `run_all.sql` rebuilds everything, so tests always start from the same data.
- Each test prints a `=====` heading and the result, or "Caught: <error>".
- Success tests cover the normal path of every program. Error tests trigger every error code (−20001 to −20016), plus the bulk DML error, the predefined exceptions `NO_DATA_FOUND` and `TOO_MANY_ROWS`, and the "no silent NULL" case in SQL.
